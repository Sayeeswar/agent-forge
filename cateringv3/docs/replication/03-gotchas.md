# Gotchas — What Went Wrong, What Fixed It

Highest-value file. Every real bug/dead-end/correction from this build.

## Reflex state & mutation

- **Mutable class-level defaults with pre-seeded nested data are risky.** `orders: list[dict] = []` starting empty and getting populated via an `on_load` handler is safe (matches Pydantic's per-instance mutable-default handling for the *empty* case). Pre-populating a class-level default directly with nested dicts (e.g. `orders: list[dict] = MOCK_ORDERS_WITH_NESTED_ITEMS` as the literal default) risks shared references across sessions since Reflex/Pydantic's mutable-default protection isn't guaranteed to deep-copy nested structures. **Fix:** always seed via an idempotent `on_load` event handler (`if not self.orders: self.orders = copy.deepcopy(...)`), never as a pre-populated class attribute default.
- **Circular imports between sibling state files.** `AdminNavState.load_admin_data` needs to call `AdminOrdersState`/`AdminMenuState`, which don't import `AdminNavState` back — but importing them at module top-level in `adminnavstate.py` before they exist (or in the wrong task order) breaks. **Fix:** import them *inside* the method body (local import), same pattern the customer app already used in `customerorderstate.py`'s `_reset_packing` for `CustomerPackingState`.
- **Nested dict/list mutation inside `list[dict]` state vars works.** `order["struck_item_ids"].append(item_id)` on an item inside `self.orders` (a `list[dict]`) correctly triggers reactivity — this is a proven, safe pattern in this Reflex version, not something to route around with full-list reassignment.

## Reflex rendering / Vars

- **`rx.cond` branches must be consistent types when the condition is a Var, not a Python bool.** A component prop like `background=rx.cond(active, COLORS["ink"], "transparent")` works when `active` is a Var (e.g. `AdminNavState.section == "orders"`). Passing a plain Python `True`/`False` as `active` for rows that are permanently on/off (Customers/Payments/Settings nav rows) also works *as long as it's fed into the same `rx.cond` call shape* — don't mix a Python `if/else` branch with a Var-based one inside the same helper function reused for both cases.
- **Choosing between two different event handlers on one button doesn't work via `rx.cond` on `on_click`.** `on_click` needs one fixed handler per button at build time. **Fix:** render two separate `rx.button` components, switched by `rx.cond` at the component level (one with `on_click=save_partial`, one with `on_click=mark_completed`), not one button with a conditionally-selected handler.
- **Event handler currying is real and is the correct pattern for foreach rows.** `on_change=AdminMenuState.update_name(item_id)` — where `update_name(self, item_id, value)` takes one more arg than what's bound — auto-appends the runtime DOM value as the final positional arg. This is *not* a lambda; passing the partially-applied handler directly as the prop value is correct and is how the customer app already does `on_click=OS.dec(item_id)` for click (no runtime value) and how admin extended it for change events (with a runtime value).
- **Computed vars with a leading underscore (`_active_source`) compile fine** as a private/internal computed var consumed only by other computed vars in the same class — never rendered directly in the component tree. Confirmed via successful import; watch for this if upgrading Reflex versions.
- **`rx.badge` accepts an `int`-typed Var directly** (`rx.badge(AdminOrdersState.total_count)`), same as the customer app's existing `rx.badge(OS.cart_count)` in `header.py` — don't assume you need `.to(str)` first; verify against the existing precedent instead of guessing.
- **Dual-mode row rendering (view vs. edit) must branch at the tab level, not per-row.** `editable` is a plain Python bool decided once when the parent page builds the `rx.foreach` call for the *current tab* — wrap two separate `rx.foreach(...)` calls in an outer `rx.cond(tab == "edit", ..., ...)`, don't try to pass a per-row Var into a Python `if/else` inside the row-render function.

## Reflex process / tooling

- **`reflex compile --dry` is fast (~5s); `reflex run --env prod --single-port` is slow (~40s)** because it does a full production build, not just a compile check. Don't assume a quiet server process crashed — poll `reflex.log` for `"App running at"` before concluding failure.
- **Backgrounding `reflex run` with `&` + `disown` in Git Bash makes the harness's background-task wrapper report "completed" almost immediately** — that's the *wrapper script* finishing, not the server. The server itself is still running detached. Check `reflex.log` content / listening port, not the task-completion status, to know if the server is actually up.
- **A stray "Connection Error" banner can appear in the accessibility tree right after navigation** even when the websocket connects fine a moment later and all data loads correctly. Don't treat it as a blocker — wait a couple seconds and re-snapshot before concluding something's broken.

## Directory / git structure

- **The git repo root is the user's home directory, not the project folder.** `git rev-parse --show-toplevel` returned `C:/Users/sayee`, with the actual Reflex project living at `cateringv3/` inside that. This means git-relative paths shown in `git status`/`git diff` output have one more path segment than you'd expect from `pwd` inside the project folder. **Fix:** always run `pwd` and `git rev-parse --show-toplevel` together before trusting a relative path in a git command output.
- **A folder rename can sit uncommitted in the working tree indefinitely without anyone noticing**, if nobody runs a full `git status` on that specific subtree. The customer app's `pages/` folder had already been renamed to `customersec/` (with `cateringv3.py`'s imports updated to match) as a pre-existing *uncommitted* change, discovered only when a new task's `ls pages/` came up empty. **Fix:** `git status` the specific directories a plan is about to touch before trusting the plan's assumed file layout, especially in a long-running session where CLAUDE.md/guard-rail docs may have been edited out-of-band.
- **When your own commit's target file also carries someone else's unrelated uncommitted change, split the commit.** Don't fold a pre-existing pending change (that isn't part of your task) into your own commit message — commit it separately first, under an accurate message, then layer your change on top.

## Design-capture tooling

- **`WebFetch` cannot render Claude Artifacts.** They're client-rendered React bundles (gzip+base64-packed JS in a `<script type="__bundler/manifest">` tag) — a static fetch only returns the loader shell and page `<title>`, never the actual rendered UI. **Fix:** use Playwright (`browser_navigate` + `browser_snapshot`/`browser_take_screenshot`), and wait ~8-15s for the bundle to unpack and the React app to mount before snapshotting.
- **A Playwright browser session can be shared with a real, visible browser window a human is also using.** Mid-smoke-test, an order-detail sheet appeared already open with an item struck, without any click from the agent — later confirmed as manual interaction in the same browser instance, not a bug. Sanity-check unexpected state against the app's own math (does the total change match excluding exactly the apparently-struck item's price?) before assuming something broke.
